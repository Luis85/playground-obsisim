# Spec: Increment 1.5 — Hardening & Polish

**Date:** 2026-07-30
**Status:** Approved scope, pre-implementation
**Predecessor:** Increment 1 (Economy Core), merged in PR #2
**Source of findings:** `docs/superpowers/reviews/2026-07-03-increment-1-multi-perspective-review.md`

---

## 1. Why this increment exists

Increment 1 shipped a working economy core and then a six-perspective review
took it apart. The review's *engineering* verdicts were good-to-excellent
(architecture strong, security low-risk, performance a non-issue at any
realistic scale, tests strong rather than merely green). Its **prioritized
action list** put five small items "before or at the start of increment 2":

| # | Review item | Status today |
|---|---|---|
| 1 | Save-migration seam (discriminated union + identity `migrate()`) | **open** |
| 2 | Array-length caps in the save guard | **done** post-merge (`MAX_SAVED_ENTITIES`) |
| 3 | The three killer tests for the survived mutations | **open** |
| 4 | Consolidate entity-fact gathering (+ gate the post-step refresh) | **partly done** — aggregation shared via `buildEntitySections`, fact gathering still duplicated, refresh still ungated |
| 5 | UX cheap-wins batch (success notices, humanized labels, hunger coloring, starter hint) | **open** |

This increment closes items 1, 3, 4 and 5, plus the review's one remaining
security finding (unbounded `CommandQueue.pending` while paused). It adds
**no new game mechanics** — that is deliberate. It is the last cheap moment
to do this work.

### 1.1 Why now, specifically

Increment 2 (Survival & Population) adds save fields on its first day:
housing, age, health. Bumping `SaveGameV1` to `v2` with today's code routes
**every existing save** through `main.ts`'s corrupt-backup path — silent data
loss for anyone already playing. The migration seam is worth an hour now and
is worth a bug report and a lost colony later. The remaining items follow the
same logic: each is a small edit today that a larger increment turns into a
multi-site edit or a regression.

### 1.2 Explicitly out of scope

Everything that changes what the player does: sinks/scarcity, food
repositioning, tools opportunity cost, farm resizing, food-gated recruiting,
`hungerRestore` on `ResourceDef`, housing, demographics, seasons. Those are
Increment 2's design decisions and get their own spec. Also out of scope:
table virtualization, the command-registry pattern, `BALANCE` as an injected
world resource, onboarding flow (all filed under "later, when the trigger
arrives" in the review).

## 2. Requirements

### 2.1 Save-migration seam (review action 1)

**Problem.** `SaveGameV1` has version scaffolding but no migration
machinery. `main.ts:loadSave()` calls `isLoadableSave(data.save)` — a type
guard that hard-requires `version === 1`. Any other version is
indistinguishable from corruption.

**Requirement.** Loading a save becomes *migrate, then validate*:

1. A versioned save of any **known** version is structurally validated
   against that version's own guard, then run through the ordered chain of
   migration steps up to the latest version.
2. The migrated result is validated by the existing catalog-aware
   `isLoadableSave` before it reaches `createColonyWorld`.
3. An unknown, unversioned, or structurally invalid save is rejected exactly
   as today: backed up to `corruptBackup`, fresh colony, `Notice` (spec §7.2).
4. A migration step that **throws** is treated as an unloadable save, not as a
   crash. Left uncaught, the exception escapes `loadSave()` and lands in
   `GameView.onOpen`'s catch: the view fails to open *and* the backup path never
   runs, leaving the player with an unloadable save and a plugin that will not
   start. A faulty migration must degrade to "start fresh", never to "cannot
   open" — migrations are hand-written code operating on old, real player data,
   so this is the failure mode most likely to actually occur.

**Constraints.**
- The chain must be **proven, not just scaffolded**. With one version today,
  an identity chain is untestable in itself, so the migration *runner* is
  exported separately and tested against an injected two-step fake chain.
  A future `v1 → v2` step then plugs into machinery that already has tests.
- **Steps advance exactly one version, and every hop is validated.** A step
  declaring `{ from: 1, to: 3 }` is refused rather than applied: it would land
  on a passing v3 guard with v2's transformation never run and v2's guard never
  checked, silently skipping a required upgrade. Each step's output must
  satisfy the guard for the version it claims, so a buggy step fails at its own
  hop instead of at the end of the chain.
- Migration is pure structure — no catalog knowledge, no balance knowledge —
  so it lives in `src/shared/`, and the catalog-aware validation stays in the
  engine. Layering (`shared` imports nothing) is unchanged.
- `serialize()` always writes the latest version. Saves never round-trip
  downward.

**Acceptance.** A v1 save loads byte-identically to today. A `version: 99`
save takes the backup path. The runner applies steps in order, stops at the
target version, and refuses a chain with a gap, a step that jumps a version, or
a step whose output fails the guard for the version it claims.

### 2.2 The three killer tests (review action 3)

Hand-run mutation testing killed 7 of 10 mutants. The 3 survivors are all
"the assertion is already true independent of the mechanism". Each gets the
test that kills it. **No production behavior changes** — if any of the three
fails as written, that is a real bug and it gets fixed in this increment.

1. **Hunger meal-threshold gate** (`hunger-system.ts:15`). Every existing
   test either crosses the threshold or has no food, so deleting the
   `continue` guard changes nothing. Killer: a well-fed worker (hunger below
   the threshold) **with bread in stock** must not eat.
2. **`buildSaveFromWorld`'s sorts** (`game-engine.ts:36-37`). Entity
   iteration order happens to equal id order in every test. Killer: restore a
   save whose worker/building records are listed out of id order, serialize,
   and assert ascending ids.
3. **`flush()`'s settle await** (`game-engine.ts:117`). Never exercised with
   a genuinely in-flight tick. Killer: start a step without awaiting it,
   dispatch a command, `await flush()`, and assert the command was applied —
   without the settle, `stepOnce()`'s re-entrancy guard swallows the extra
   tick and the command is silently dropped.

### 2.3 Entity-fact gathering and the per-tick refresh (review action 4)

**Problem.** Two convergent findings hit the same code. Architecture: every
new worker field is a 3-site edit (`SnapshotSystem`, `refreshEntitySections`,
`buildInitialSnapshot`) — 4 counting `buildSaveFromWorld`. Performance:
`refreshEntitySections` re-walks every entity after **every** tick, but it
only exists to catch entities that the tick's own commands created.

**Requirement.**
- **One per-entity mapper, not one walk.** Component → facts conversion lives
  in exactly one function per entity kind (`workerFactsOf`, `buildingFactsOf`),
  called by *both* live-world access paths: `SnapshotSystem`'s ECS queries and
  the `getEntities()` walk that `refreshEntitySections` and
  `buildSaveFromWorld` share. A new worker field is then one edit for the whole
  live world, not one per access path.
- `refreshEntitySections` runs only on ticks that actually changed the entity
  set. Detection uses the id counter: entity creation is the only thing that
  consumes ids, so a `peek()` delta across `step()` is an exact signal today.
- The gate carries a written invariant for Increment 2: the first system that
  **removes** an entity must extend the signal, because a removal consumes no
  id. This is stated in code, next to the gate, not only in docs.

**Why not literally one function.** Two constraints pull against each other,
and the resolution is deliberate:

- `SnapshotSystem` keeps its **queries** rather than switching to the shared
  `getEntities()` walk. Queries are the ECS-idiomatic path, and keeping
  SnapshotSystem's in-tick entity work is precisely what makes *skipping* the
  post-step refresh safe — a skipped refresh must not leave stale sections
  behind. Consolidating the walk instead of the mapper would trade the
  performance finding straight back for the architecture one. Sharing the
  per-entity mapper gets the drift protection without that trade.
- `buildInitialSnapshot` maps **save records**, not components — at that point
  no entities exist yet — so it cannot share a component mapper by
  construction. It stays a separate single site, alongside the `SavedWorker`
  record type it reads.

So a new worker field costs exactly two edits after this increment (the live
mapper, and the save record + its initial-snapshot mapping), down from four
today. Claiming "one site" would be false; two is the real floor while saves
exist.

**Acceptance.** Snapshots are byte-identical to today's on every tick,
including the tick that constructs a building or recruits a worker. Every
component read for the live world goes through the shared per-entity mappers —
no `getComponent`/query destructuring of worker or building fields outside
them. A refresh happens on entity-creating ticks and is skipped otherwise,
asserted by test.

### 2.4 Bounded command queue (review security L1)

`CommandQueue.pending` grows without limit while paused (the UI leaves
buttons enabled). Cap it: past the cap, further dispatches are dropped and
one notice explains why. The cap is high enough that no human clicking can
reach it and low enough that the queue can never be a memory story.

### 2.5 UX cheap wins (review action 5)

Increment 1's UI reports failure and stays silent on success. Five changes,
all inside existing plumbing:

1. **Success feedback.** Notices gain a kind (`success` | `rejection`).
   Accepted commands push a success notice ("Built a Sawmill.", "Recruited
   worker #4.", …) through the same channel rejections already use, styled
   distinctly. This is a `Snapshot` contract change: `notices: string[]` →
   `notices: NoticeMessage[]`.

   **Prerequisite bug fix — notices are re-appended on status-only publishes.**
   `GameEngine.publish()` re-sends the *current* snapshot object on `start()`,
   `pause()`, `setSpeed()` and on listener registration, and the store's
   `ingest` appends `snapshot.notices` every time it is called. So a tick that
   produced a notice, followed by any speed/pause click, duplicates that
   notice — including its Vue `:key` (tick + message). Reproduced against
   today's code: two `ingest` calls with one snapshot object yield two
   identical `recentNotices` entries. This is live today for rejections and
   would fire constantly once every accepted command emits one, so it is fixed
   as part of this item: notices are ingested only when the snapshot is a new
   one, compared by raw object identity (`toRaw`, because Pinia state hands
   back a reactive proxy — verified: direct `===` is always false, `toRaw(…) ===`
   is true).

   **And each notice carries a unique id.** One tick drains every command
   queued since the last one, so two identical commands (two assign clicks on
   the same building — trivial while paused) emit two byte-identical notices in
   the same tick. Keying the rendered list on tick + kind + message would give
   Vue duplicate keys and let it reuse or drop rows; a store-monotonic id is
   unique by construction. Also reachable today with two identical rejections
   in one tick.
2. **Humanized building states.** `waitingForInput` currently renders raw.
   Labels are a presentation concern, so the map lives in `src/app/`, not in
   the engine or the contract.
3. **Hunger legibility.** Hunger (higher = worse) sits unstyled next to
   efficiency (higher = better). Cells at or past the meal threshold get a
   warning class; near the cap, a stronger one.
4. **Starter hint.** With zero buildings, the Buildings view says what to do
   first (a forester or gatherer's hut, and that idle workers need assigning)
   instead of only "No buildings yet".
5. **Reset needs a real confirmation.** `window.confirm` is one Enter press
   from wiping a colony. Replace it with a two-step in-app arm/confirm (with
   an explicit cancel), which is also testable without stubbing globals.

Plus one hardcode removal that is pure cleanup: the store's `lowFood` getter
hardcodes `bread + berries`; `ResourceDef.edible` already exists and should
drive it. (Generalizing *hunger restoration* stays in Increment 2 — this is
only the "which resources count as food" question.)

## 3. Non-goals for the implementation

- No balance number changes. `BALANCE` and the content catalog are untouched,
  so no save written by Increment 1 can be invalidated by this increment.
- No new dependencies.
- No changes to system execution order (spec §4.4).
- Quality-gate baselines are not loosened. `maintainability` may only ratchet
  up; `complexFunctions` / `criticalComplexity` / `boundaryViolations` stay 0.

---

## 4. Acceptance criteria

Increment 1.5 is done when:

1. A save written by Increment 1 loads with identical in-world state, and a
   save with an unknown version takes the corrupt-backup path.
2. The migration runner is covered by tests that would fail if steps were
   applied out of order, skipped, or run past the target version.
3. The three killer tests exist and pass; re-applying each mutation by hand
   fails at least one test.
4. Every live-world component read for worker/building facts goes through one
   shared per-entity mapper (queries and the `getEntities()` walk alike), and
   the post-step refresh is provably skipped on ticks that create no entity.
5. `CommandQueue.pending` is bounded, with a notice on overflow.
6. The five UX changes are visible in the plugin and covered by component
   tests; success and rejection notices are visually distinct, and a
   status-only publish (pause / speed change) never duplicates a notice.
7. `npm run check:all` and `npm run test:coverage` pass; no baseline is
   loosened.
